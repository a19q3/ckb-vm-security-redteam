# CKB-VM Security Red Team Findings Report

Date: 2026-06-04
Target: `ckb-vm` branch `develop`, commit `d1a1cfc`
Method: static analysis, baseline tests, ASM-enabled tests, and malformed ELF harness

## Summary

| Severity | Count | Status |
|---|---:|---|
| High | 1 | Verified |
| Medium | 3 | Verified |
| Low | 2 | Verified |

Validation:

- `cargo test` passed.
- `cargo test --features detect-asm` passed.
- Malformed ELF harness confirmed loader findings.

## High

### H1: ELF loader executes bytes beyond `p_memsz` when `p_filesz > p_memsz`

Surface: ELF
Location: `src/elf.rs:181-203`, `src/memory/mod.rs:86-105`

The loader accepts a `PT_LOAD` segment whose file size is larger than its declared memory size. If the segment is executable, ckb-vm materialises the full file slice into an executable page and begins executing it.

Evidence:

```text
exec_filesz_gt_memsz: parse=Ok(... size: 4096, source: 256..272 ...)
exec_filesz_gt_memsz: load=Ok(16); pc=0x10000
exec_filesz_gt_memsz: mem[0x10000..+16]=Ok(b"\x01\x02...\x10")
exec_filesz_gt_memsz: first_step=Ok(()); pc_after=0x10002
```

Recommendation: reject `PT_LOAD` segments with `p_filesz > p_memsz`, and use checked arithmetic for segment extent and page rounding.

## Medium

### M1: ELF entry point is not validated against loaded executable segments

Surface: ELF
Location: `src/elf.rs:135-209`, `src/machine/mod.rs:140-170`

An ELF with `e_entry` outside all loaded segments is accepted by the loader and only fails when execution tries to fetch from the invalid PC.

Evidence:

```text
entry_outside_load: load=Ok(4); pc=0xdead0000
entry_outside_load: first_step=Err(MemOutOfBound(3735879680, Memory))
```

Recommendation: require `e_entry` to fall inside a loaded executable `PT_LOAD` range.

### M2: ELF segment size arithmetic can wrap to zero

Surface: ELF
Location: `src/elf.rs:183-185`, `src/bits.rs:1-6`

`p_memsz.wrapping_add(padding_start)` and `round_page_up` can turn an oversized segment into a zero-sized loading action.

Evidence:

```text
wrapped_memsz: parse=Ok(... size: 0, source: 256..257 ...)
wrapped_memsz: load=Ok(1); pc=0x10000
wrapped_memsz: first_step=Err(MemWriteOnExecutablePage(16))
```

Recommendation: replace wrapping arithmetic with checked arithmetic and reject rounded sizes that overflow or shrink.

### M3: Zero-memory `PT_LOAD` segments with non-zero file data are accepted

Surface: ELF
Location: `src/elf.rs:181-203`, `src/machine/mod.rs:140-170`

`p_memsz = 0` with `p_filesz > 0` produces a zero-sized loading action with a non-empty source range. Loading reports success and commits PC even though no page was initialised.

Evidence:

```text
zero_memsz_nonzero_filesz: load=Ok(16); pc=0x10000
zero_memsz_nonzero_filesz: mem[0x10000..+16]=Ok(b"\0"...)
zero_memsz_nonzero_filesz: first_step=Err(MemWriteOnExecutablePage(16))
```

Recommendation: reject `p_memsz == 0 && p_filesz > 0`.

## Low

### L1: Failed SC still performs a same-value store and marks the page dirty

Surface: Instructions / Snapshot
Location: `src/instructions/execute.rs:257-268`, `src/instructions/execute.rs:388-399`

Failed `SC.W` and `SC.D` load the existing memory value and store it back, which dirties the page even though the architectural memory value is unchanged.

Recommendation: on failed SC, set `rd = 1`, clear LR, and return without writing memory.

### L2: Memory constructors panic on non-page-aligned sizes

Surface: Memory
Location: `src/memory/sparse.rs:73`, `src/memory/flat.rs:35`

`SparseMemory::new` and `FlatMemory::new` enforce page alignment with `assert!`, which is brittle for embedders and fuzz harnesses.

Recommendation: expose fallible constructors or document the panic contract explicitly.

## Removed False Positives

- SparseMemory u16 page-index truncation was not established and should not be reported without a current-version proof.
- WXorX read-from-executable is not a WXorX violation; WXorX is write-xor-execute, not read-xor-execute.
- Bare `SparseMemory`/`FlatMemory` lack WXorX by design; the normal public runner wraps memory in `WXorXMemory`.
- RISC-V signed `DIV/REM` overflow is defined behaviour, not a required trap.
- Snapshot and Snapshot2 both serialise `load_reservation_address`.
