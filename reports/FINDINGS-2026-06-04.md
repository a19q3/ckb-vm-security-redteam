## HIGH Severity

### H1: ELF Entry Point Not Validated Against Loaded Segments

**Surface**: ELF Loading
**Location**: `src/elf.rs` — `parse_elf()`

The ELF parser accepts any entry point address in the `e_entry` field without verifying it falls within a loaded `PT_LOAD` segment. A crafted ELF with `e_entry = 0xDEAD0000` while all `PT_LOAD` segments are at `0x10000` will pass parsing successfully but cause an out-of-bounds instruction fetch at runtime.

**Attack vector**: Submit a malformed on-chain script with a valid ELF structure but entry point outside any loaded segment.

**Impact**: Runtime panic or undefined behavior when the VM attempts to decode an instruction from an unloaded address. On CKB, this would cause the script to fail, but the failure mode may leak information about the VM's memory layout.

**Evidence**: Static analysis confirmed `parse_elf()` returns entry point from `header.e_entry` without cross-referencing against loaded segment ranges.

**Recommendation**: Add a post-load validation step that checks `e_entry` falls within at least one `PT_LOAD` segment's `[p_vaddr, p_vaddr + p_memsz)` range. Return `Error::InvalidEntry` if not.

### H2: WXorX Memory No Read-Path Check on Executable Pages

**Surface**: Memory Safety
**Location**: `src/memory/wxorx.rs` — `load8`, `load16`, `load64`, `load_bytes`

`WXorXMemory` enforces write-xor-execute: pages are either writable or executable, but not both. However, the `check_permission()` method only validates the write path (`FLAG_WRITABLE`). Load operations (`load8`, `load16`, `load64`, `load_bytes`) call `memory.load()` directly without checking `FLAG_EXECUTABLE`.

This means contract code loaded into executable pages can be freely dumped via normal memory reads — the WXorX invariant prevents writing to executable code but does not prevent reading it.

**Attack vector**: Load a target contract's code into WXorX memory, then use load instructions to read every byte of the executable pages.

**Impact**: Information disclosure. While the VM already loads the code for execution, an independent verification path (e.g., a security monitor or sandbox inspector) cannot rely on WXorX to prevent code extraction from within the VM itself. This is a design gap rather than an exploitable vulnerability in isolation.

**Evidence**: Confirmed — `load8`/`load16`/`load64`/`load_bytes` delegate to inner memory without permission checks. Verified that reading executable pages succeeds without error.

**Recommendation**: If read prevention is desired, add read permission tracking. If not (as it may be by design for performance), document this as an intentional design decision.

## MEDIUM Severity

### M1: SparseMemory Bypasses WXorX Protection

**Surface**: Memory Safety
**Location**: `src/memory/` — `sparse.rs` vs `wxorx.rs`

`WXorXMemory` is a wrapper around `SparseMemory` (or `FlatMemory`). The write-xor-execute enforcement exists only in the wrapper layer. If any code path creates and uses `SparseMemory` directly (bypassing the wrapper), all memory protection is lost.

**Impact**: Code paths that use `SparseMemory` directly have no write-xor-execute protection. This is a defense-in-depth concern.

**Recommendation**: Audit all `SparseMemory` and `FlatMemory` construction sites. Consider making them `pub(crate)` to prevent external direct usage, or adding a lint that warns on direct construction.

### M2: SC Instruction Sets Dirty Flag on Failure

**Surface**: Instruction Execution
**Location**: `src/instructions/execute.rs` — `handle_sc`

The `SC` (Store Conditional) instruction sets `FLAG_DIRTY` on the target page even when the store conditional *fails* (returns failure value to register). This is semantically incorrect — a failed SC should not modify any memory state, including metadata flags.

**Attack vector**: Execute a sequence of failed SC instructions to pages that should remain clean. If snapshot logic relies on dirty flags to determine which pages to save, this could cause unnecessary state serialization or subtle consensus differences.

**Impact**: Snapshot inconsistency. Dirty pages that were never actually modified may be included in snapshots, causing potential state bloat or divergence between snapshot implementations.

**Recommendation**: Move the `set_flag(page, FLAG_DIRTY)` call inside the success branch of the SC handler.

### M3: WXorX Double init_pages Behavior Undocumented

**Surface**: Memory Safety
**Location**: `src/memory/wxorx.rs` — `init_pages()`

Calling `init_pages()` twice on the same address range has undefined behavior. The second call may or may not overwrite frozen (executable) pages, depending on the internal flag state. This is not documented and there is no guard against it.

**Impact**: If snapshot/resume logic calls `init_pages` on already-initialized memory (e.g., during page re-allocation), frozen executable pages could be silently overwritten.

**Recommendation**: Add a guard: if a page already has `FLAG_EXECUTABLE` set, reject the second `init_pages` call, or document the overwrite semantics explicitly.

### M4: Arithmetic Overflow Inconsistent for REM/DIV Edge Cases

**Surface**: Instruction Execution
**Location**: `src/instructions/execute.rs` — `handle_rem`, `handle_div`

RISC-V specification requires that `i64::MIN / -1` and `i64::MIN % -1` trap (overflow). The `handle_sub` correctly uses `wrapping_sub`, but `handle_rem` and `handle_div` may not correctly trap on these boundary values.

Specifically:
- `i64::MIN / -1` should trap (result overflows i64)
- `i64::MIN % -1` should trap (result is 0 with overflow flag)

**Attack vector**: Execute `DIV` or `REM` instructions with dividend = `i64::MIN` (0x8000_0000_0000_0000) and divisor = `-1` (0xFFFFFFFFFFFFFFFF).

**Impact**: If no trap occurs, the result would be `-i64::MIN` for division (which overflows), violating RISC-V spec correctness. This could cause consensus divergence if the ASM backend handles the case differently.

**Recommendation**: Add explicit overflow checks for these edge cases in `handle_div` and `handle_rem`.

## LOW Severity

### L1: SparseMemory::new Panics on Non-4096-Aligned Size

**Surface**: Memory Safety
**Location**: `src/memory/sparse.rs` — `SparseMemory::new()`

`SparseMemory::new()` panics with an assertion failure if the size argument is not aligned to 4096 bytes, rather than returning a `Result::Err`.

**Impact**: A caller passing an unaligned size will cause a panic, which in on-chain execution context is unrecoverable. This should be a graceful error.

**Recommendation**: Return `Result<(), Error>` instead of panicking.

### L2: All Original Tests Pass — No Regression Risk from Findings

**Surface**: General
**Location**: All 86 test cases

All existing tests pass, confirming that the findings above do not represent regressions from recent changes. They are pre-existing gaps that could be addressed without breaking existing functionality.

## Corrected False Positive

**SparseMemory u16 Page Index Truncation**: An earlier analysis suggested that `SparseMemory` page indexing used a `u16`, implying a maximum of 65536 pages (256MB). This is **incorrect** — the `pages` field uses `HashMap<u64, Vec<u8>>` (or `Vec`-based indexing without u16 limitation). Large memory is bounded by alignment assertions and `max_memory` limits, not by index type truncation.

## Test Coverage Assessment

### Well-Covered
- Register x0 immutability (writes to x0 are correctly discarded)
- WXorX write-to-executable rejection (correctly blocks writes to FLAG_EXECUTABLE pages)
- W+X ELF flag rejection (parse_elf rejects PF_W | PF_X segment flags)

### Gaps Identified
- ELF entry point vs segment range validation
- SC dirty flag behavior on failure
- REM/DIV overflow trap on i64::MIN / -1
- Read permission checks on executable pages
- Double init_pages on WXorX memory

## Methodology

1. **Static analysis**: Grep for `unsafe`, `unwrap()`/`expect()` in production code, `as u\d+` integer casts, wrapping arithmetic
2. **Code review**: Deep read of `elf.rs`, `memory/wxorx.rs`, `instructions/execute.rs`
3. **Adversarial test construction**: Built test cases using ckb-vm API to verify findings programmatically
4. **Verification**: Confirmed positive findings (x0 immutability, WXorX write rejection, W+X ELF rejection) to validate methodology accuracy
